# API & Integration Guide

## Overview

This is a real-time AI messaging service and progressive web application where human users interact with AI bots and autonomous coding agents. The service provides a responsive web interface along with comprehensive REST endpoints and WebSocket channels supporting two primary integration modes:
1. **Chat Protocol**: For conversational assistants (OpenAI, Anthropic, Gemini, local models) with model choices, optional context window sizes, markdown formatting, syntax highlighting, and suggestions.
2. **Agent Host Protocol (AHP)**: For programming and coding agents (Claude Code, Devin, custom coding harnesses) with active sub-chat sessions, streaming reasoning/thinking tokens, tool step progress, human-in-the-loop question approvals, mid-turn steering, prompt queuing, and bot protocol badges.

**Base URL:** `http://localhost:4002` (docker / production port) or `http://localhost:4000` (dev)

---

## Authentication

There are two types of authentication:

### User Authentication (email/password → session token)

Users register and log in with email/password. The server returns a Bearer token used for subsequent requests.

```
Authorization: Bearer <USER_TOKEN>
```

### Bot Authentication (generated token)

Bots authenticate with a token generated by a user via the API or web UI. The token is shown once at creation time or regenerated on demand.

```
Authorization: Bearer <BOT_TOKEN>
```

### Create Bot Token

```http
POST /api/bot-tokens
Authorization: Bearer <USER_TOKEN>
Content-Type: application/json
```

```json
{
  "name": "my-coding-agent",
  "bot_type": "ahp",
  "metadata": {"project": "ai-messaging-service"}
}
```

- `bot_type` (optional, string): `"chat"` (default) or `"ahp"`. Controls whether the bot operates in standard conversational mode or multi-session coding agent mode with sub-chats.
- `metadata` (optional, object): Arbitrary JSON metadata for the bot.

**Response (201):**

```json
{
  "id": 1,
  "name": "my-coding-agent",
  "token": "BOT_TOKEN_SHOWN_ONCE",
  "channel_code": "CHANNEL_CODE_FOR_WEBSOCKET_JOIN",
  "bot_type": "ahp",
  "metadata": {"project": "ai-messaging-service"}
}
```

### Create Conversation

```http

Authorization: Bearer <USER_TOKEN>
```

### Upload Asset (Image/File)

Users can upload images or files to a conversation before sending them to the bot.

```
POST /api/conversations/:conversation_id/assets
Authorization: Bearer <USER_TOKEN>
Content-Type: multipart/form-data
```

**Request:**
- `file`: The file to upload (required). Allowed types: JPEG, PNG, WebP, GIF, PDF, plain text, CSV

**Response (201):**

```json
{
  "url": "/uploads/:conversation_id/filename-timestamp.ext",
  "content_type": "image/jpeg",
  "filename": "screenshot.jpg"
}
```

Then send a message with the asset:

```
POST /api/conversations/:conversation_id/messages
Authorization: Bearer <USER_TOKEN>
Content-Type: application/json
```

```json
{
  "asset_url": "/uploads/1/screenshot-1715427000000.jpg",
  "asset_type": "image",
  "asset_filename": "screenshot.jpg",
  "model": "gpt-4o",
  "context_size": 32768

```

The `asset_type` can be `"image"` for image files or `"file"` for other file types. Images will be displayed inline in the chat; files will be shown as downloadable links.

**Response (201):**

```json
{
  "id": 2,
```

## Content Types

The `content_type` field controls what the user sees. Each type has specific field requirements.

### `text`

Plain text message. `body` is required.

```json
{
  "conversation_id": 5,
  "content_type": "text",
  "body": "Hello, how can I help?"
}
```

### `image`

An image. `metadata.url` is required. `body` is an optional caption.

```json
{
  "conversation_id": 5,
  "content_type": "image",
  "body": "Here is the chart you asked for",
  "metadata": {
    "url": "https://example.com/chart.png"
  }
}
```

### `video`

A video. `metadata.url` is required. Optional `metadata.mime_type` (defaults to `video/mp4`). `body` is an optional caption.

```json
{
  "conversation_id": 5,
  "content_type": "video",
  "body": "Demo recording",
  "metadata": {
    "url": "https://example.com/demo.mp4",
    "mime_type": "video/mp4"
  }
}
```

### `file`

A downloadable file. `metadata.url` is required. Optional `metadata.filename`. `body` is an optional description.

```json
{
  "conversation_id": 5,
  "content_type": "file",
  "body": "Export complete",
  "metadata": {
    "url": "https://example.com/report.pdf",
    "filename": "report.pdf"
  }
}
```

### `actions`

Suggested follow-up actions rendered as clickable buttons. `metadata.actions` is required (array of objects with `label`). `body` is an optional prompt shown above the buttons. When the user clicks an action, it sends the label text back as a normal user text message.

```json
{
  "conversation_id": 5,
  "content_type": "actions",
  "body": "What would you like to do next?",
  "metadata": {
    "actions": [
      {"label": "Show more details"},
      {"label": "Start over"},
      {"label": "Export as PDF"}
    ]
  }
}
```

## WebSocket API (real-time)

Connect to the Phoenix socket for real-time bidirectional messaging. Messages from the user are pushed to the bot instantly instead of requiring polling.

### Connect

```
ws://<HOST>:4000/bot/websocket?token=<BOT_TOKEN>
```

The server marks the bot as connected on successful handshake.

### Join your channel

After connecting, join your bot's channel. Use the `channel_code` retrieved from `GET /api/bot-tokens/:id/channel`. This keeps your authentication token private and out of the channel topic.

Phoenix channel join message:

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "phx_join",
  "payload": {},
  "ref": "1"
}
```

### Receive user messages

The server pushes `new_message` events when a user sends a message:

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "new_message",
  "payload": {
    "conversation_id": 5,
    "message": {
      "id": 1,
      "role": "user",
      "content_type": "text",
      "body": "Hello bot!",
      "metadata": {},
      "model": "gpt-4o",
      "context_size": 32768,
      "inserted_at": "2026-05-11T18:30:00Z"
    }
  }
}
```

### Send a message (WebSocket)

Push a `send_message` event to reply:

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "send_message",
  "payload": {
    "conversation_id": 5,
    "content_type": "text",
    "body": "Here is my answer."
  },
  "ref": "2"
}
```

Reply on success:

```json
{
  "event": "phx_reply",
  "payload": {"status": "ok", "response": {"id": 2}},
  "ref": "2"
}
```

### Acknowledge a message (WebSocket)

Push an `acknowledge_message` event to show the thinking animation in the user's chat before you send a response:

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "acknowledge_message",
  "payload": {
    "message_id": 1,
    "conversation_id": 5
  },
  "ref": "4"
}
```

Reply on success:

```json
{
  "event": "phx_reply",
  "payload": {"status": "ok"},
  "ref": "4"
}
```

### Update status

Push an `update_status` event:

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "update_status",
  "payload": {"is_working": true},
  "ref": "3"
}
```

### Receive model refresh request

The server pushes a `refresh_models` event when a user requests the bot to update its available models. The bot should respond by calling `PUT /api/bot/models` with its current model list.

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "refresh_models",
  "payload": {}
}
```

### Heartbeat

Phoenix requires a heartbeat every 30 seconds or the connection is dropped:

```json
{
  "topic": "phoenix",
  "event": "heartbeat",
  "payload": {},
  "ref": "hb"
}
```

## Typical Bot Loop (REST polling)

```
1. GET  /api/bot/messages?since=<last_seen_timestamp>
2. For each message:
   a. PUT  /api/bot/status  {"is_working": true}
   b. Process the message
   c. POST /api/bot/messages  {response}
   d. PUT  /api/bot/status  {"is_working": false}
3. Sleep, then go to 1
```

## Typical Bot Loop (WebSocket)

```
1. Connect to ws://.../bot/websocket?token=<BOT_TOKEN>
2. GET /api/bot/channel to retrieve channel_code
3. Join channel "bot:<CHANNEL_CODE>"
4. PUT /api/bot/models with available models
5. On "new_message" event:
   a. Push "acknowledge_message" {message_id, conversation_id}
   b. Push "update_status" {"is_working": true}
   c. Process the message
   d. Push "send_message" {response}
   e. Push "update_status" {"is_working": false}
6. On "refresh_models" event:
   a. PUT /api/bot/models with current models
7. Send heartbeat every 30s
```

## Error Responses

| Status | Meaning |
|--------|---------|
| 401    | Missing or invalid bot token |
| 403    | Conversation does not belong to this bot |
| 422    | Validation error (check `errors` object in response) |

Validation error shape:

```json
{
  "errors": {
    "body": ["is required for text messages"]
  }
}
```

## Agent Host Protocol (AHP) Integration Mode

In addition to standard chat bots, the service natively supports **Agent Host Protocol (AHP)** integration for programming and coding assistants.

### 1. Bot Registration & Type

When creating a bot token, set `"bot_type": "ahp"`:

```json
POST /api/bot-tokens
{
  "name": "my-coding-agent",
  "bot_type": "ahp"
}
```

### 2. Multi-Session Synchronization (`sync_sessions`)

AHP agents report their active non-archived sessions. Each active session maps directly to a sub-chat in the service with its own live status.

Push `sync_sessions` over WebSocket (`bot:<CHANNEL_CODE>`):

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "sync_sessions",
  "payload": {
    "sessions": [
      {
        "session_id": "session-backend-refactor",
        "title": "Refactor Ecto Schemas",
        "status": "running",
        "last_user_input_time": "2026-10-07T12:30:00Z",
        "last_modified_time": "2026-10-07T12:45:00Z",
        "metadata": {
          "step": "Running mix compile",
          "tool": "run_command"
        }
      },
      {
        "session_id": "session-test-suite",
        "title": "Unit & Integration Tests",
        "status": "waiting_for_input",
        "last_user_input_time": "2026-10-07T11:45:00Z",
        "last_modified_time": "2026-10-07T12:15:00Z",
        "metadata": {
          "step": "Awaiting approval for git push",
          "question": {
            "id": "q-101",
            "title": "Git Push Confirmation",
            "prompt": "Allow pushing branch 'refactor/ahp' to remote origin?",
            "options": ["Approve", "Reject"]
          }
        }
      }
    ]
  },
  "ref": "1"
}
```

Sessions not included in subsequent `sync_sessions` calls are marked as `archived` in the service.

### 3. Session Status Updates (`session_status`)

Push status changes as the agent progresses:

```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "session_status",
  "payload": {
    "session_id": "session-backend-refactor",
    "status": "thinking",
    "metadata": {
      "step": "Analyzing dependency graph"
    }
  },
  "ref": "2"
}
```

**Supported Statuses:**
- `"idle"`: Agent is awaiting user requests. Any queued prompt is automatically dispatched.
- `"running"`: Agent is executing tools or commands.
- `"thinking"`: Agent is streaming reasoning / thinking tokens.
- `"waiting_for_input"`: Agent is awaiting user approval or question answer.
- `"archived"`: Session has ended.

### 4. Ferrying AHP Events (`ahp_event`)

Ferry raw AHP events to the service with minimal transformation:

#### a. Streaming Thinking Tokens
```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "ahp_event",
  "payload": {
    "session_id": "session-backend-refactor",
    "event_type": "thinking",
    "data": {
      "chunk": "Checking database migrations to ensure compatibility..."
    }
  },
  "ref": "3"
}
```

#### b. Tool / Step Progress
```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "ahp_event",
  "payload": {
    "session_id": "session-backend-refactor",
    "event_type": "step",
    "data": {
      "tool": "run_command",
      "command": "mix test test/messaging/chat_test.exs",
      "step": "Executing chat unit tests"
    }
  },
  "ref": "4"
}
```

#### c. Interactive Question / Approval Request
```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "ahp_event",
  "payload": {
    "session_id": "session-backend-refactor",
    "event_type": "question",
    "data": {
      "id": "q-552",
      "title": "Database Reset Approval",
      "prompt": "The test requires resetting the database. Proceed with 'mix ecto.reset'?",
      "options": ["Proceed", "Abort"],
      "default_action": "Proceed"
    }
  },
  "ref": "5"
}
```

### 5. Receiving User Interactions from the Service

The bot receives user responses pushed over the WebSocket:

#### a. Question / Approval Answer (`answer_question`)
```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "answer_question",
  "payload": {
    "conversation_id": 42,
    "question_id": "q-552",
    "answer": "Proceed",
    "approved": true,
    "comment": "Safe to proceed with test db only."
  }
}
```

#### b. Steering & Interruptions (`steer_agent`)
```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "steer_agent",
  "payload": {
    "conversation_id": 42,
    "action": "steer",
    "instruction": "Stop here and focus on the channel tests first."
  }
}
```
Or interrupt/cancel:
```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "steer_agent",
  "payload": {
    "conversation_id": 42,
    "action": "stop"
  }
}
```

#### c. Auto-Dispatched Queued Prompts (`execute_queued_prompt`)
When an agent transitions to `"idle"`, any prompts queued by the user while the agent was running are dispatched automatically:
```json
{
  "topic": "bot:<CHANNEL_CODE>",
  "event": "execute_queued_prompt",
  "payload": {
    "conversation_id": 42,
    "prompt": {
      "id": "3a8f9c12b7",
      "body": "Now update the README and test coverage docs.",
      "model": "claude-3-7-sonnet",
      "queued_at": "2026-10-06T20:15:00Z"
    }
  }
}
```

### 6. Example Python Bridge Snippet

```python
import json
import websocket

BOT_TOKEN = "your_bot_token"
CHANNEL_CODE = "your_channel_code"
WS_URL = f"ws://localhost:4002/bot/websocket?token={BOT_TOKEN}"

ws = websocket.create_connection(WS_URL)

# 1. Join bot channel
ws.send(json.dumps({
    "topic": f"bot:{CHANNEL_CODE}",
    "event": "phx_join",
    "payload": {},
    "ref": "1"
}))

# 2. Sync active coding sessions
ws.send(json.dumps({
    "topic": f"bot:{CHANNEL_CODE}",
    "event": "sync_sessions",
    "payload": {
        "sessions": [
            {
                "session_id": "session-api-refactor",
                "title": "API Refactor Task",
                "status": "running",
                "metadata": {"step": "Compiling Elixir code", "tool": "mix compile"}
            }
        ]
    },
    "ref": "2"
}))

# 3. Stream thinking
ws.send(json.dumps({
    "topic": f"bot:{CHANNEL_CODE}",
    "event": "ahp_event",
    "payload": {
        "session_id": "session-api-refactor",
        "event_type": "thinking",
        "data": {"chunk": "Analyzing module boundaries...\n"}
    },
    "ref": "3"
}))

# Listen for user interactions (answer_question, steer_agent, execute_queued_prompt)
while True:
    msg = json.loads(ws.recv())
    event = msg.get("event")
    if event == "answer_question":
        print(f"User answered: {msg['payload']}")
    elif event == "steer_agent":
        print(f"User steered agent: {msg['payload']}")
    elif event == "execute_queued_prompt":
        print(f"Executing queued prompt: {msg['payload']}")
```

## Web UI & Developer Experience Features

The PWA web application includes rich interactive controls and visual status indicators designed for both Chat and AHP agents:

### 1. Protocol Badges
In the chat header, a badge dynamically identifies the protocol type of the active bot:
- **`AHP Protocol`** (`.bot-protocol-badge--ahp`): Displayed for bots with `bot_type: "ahp"`. Highlights coding agent features (sub-chats, thinking streaming, interactive questions).
- **`Chat Protocol`** (`.bot-protocol-badge--chat`): Displayed for bots with `bot_type: "chat"`. Highlights conversational LLM features (model switching, context sizes, markdown rendering).

### 2. Bot Configuration Modal (Gear Icon ⚙️)
When any bot or sub-chat is selected, a gear icon appears in the top-right chat header. Clicking it opens the **Bot Configuration Modal**:
- **Service WebSocket URL**: Shows the exact WebSocket URL (`ws://<host>:<port>/bot/websocket?token=<BOT_TOKEN>`) ready to copy for your agent scripts.
- **Bot Channel Code**: Displays the unique `channel_code` for subscribing to the bot's private Phoenix channel (`bot:<CHANNEL_CODE>`).
- **Token Regeneration**: Provides a "Regenerate Key" button that calls `POST /api/bot-tokens/:id/regenerate`, instantly issuing a new token and channel code and displaying it once for secure copying without needing to recreate the bot.

### 3. Multi-Session Sub-Chats & Status Sidebar
For AHP bots, the sub-chat navigation drawer and sidebar display all active sessions synchronized via `sync_sessions`. Each sub-chat displays:
- **Status Pills**:
  - `Thinking`: Purple glowing badge indicating active reasoning token generation.
  - `Running`: Blue badge indicating active tool/command execution with tool step preview.
  - `Needs Input`: Amber pulsing badge indicating a human approval or question is pending.
  - `Idle`: Green badge indicating readiness for new user prompts.
- Real-time updates are broadcast to the sidebar over the `bot_sessions:<bot_id>` Phoenix channel.

### 4. Interactive Approvals & Question Cards
When the bot emits a `question` AHP event, the chat renders a `QuestionApprovalCard`:
- Shows title, prompt, description, and configurable options.
- Clicking an option button immediately dispatches an `answer_question` event back to the bot over the WebSocket (`topic: "bot:<CHANNEL_CODE>"`), unblocking the agent's workflow.

### 5. Mid-turn Steering & Prompt Queuing
- **Steering**: While an agent is running or thinking, users can submit mid-turn course corrections or click "Stop" to halt the agent, sending `steer_agent` payloads directly to the bot.
- **Prompt Queue**: Users can type and queue follow-up prompts while an agent is busy. When the bot sends `session_status` with `status: "idle"`, queued prompts are automatically dispatched one-by-one via `execute_queued_prompt`.

### 6. Context Window Size Selector
When models configured via `PUT /api/bot/models` specify `context_sizes` (e.g. `[4096, 8192, 16384, 32768, 128000]`), a context size selector dropdown appears in the chat header next to the model selector. Selected context sizes are passed with user messages as `context_size`.
